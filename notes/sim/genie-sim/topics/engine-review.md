# 仿真引擎、资源与渲染同步：工程资料摘编

本篇于 2026-10-19 根据原工程的 7 份配套文档整理。源文件捕获于提交 `5015ce3d4acc61258a0184b1a008a003f67d8a22`；各文档原研究日期和执行者身份未逐篇明确记载。原文件逻辑路径及 SHA256 见 [来源](../sources.md)与 [provenance.json](../provenance.json)。本篇属于原文审阅与摘编，没有重新检查实现、构建环境或运行引擎。

## 资源构建与消费要分别追踪

`pipeline.md` 把模型装配、场景 manifest 与运行时消费分开：场景中的 URDF 配置决定走预制资源还是 URDF → USD 路线；运行时读取已准备好的 manifest 与 USD。缓存命中与重建是不同路径，检查结果需说明使用了哪一份输入。

`asset_consumption.md` 继续追踪同一个装配输出如何被各引擎消费，以及哪些属性会由运行时覆盖。可复用的经验是：不能只在源文件中找到一个参数就认定它已经进入求解器，应沿着装配文件、已组合 stage、构建后的模型和最终求解器分别检查。

原文的碰撞策略对不同 link 采用不同处理；因此“模型有网格”“加载了机器人”和“该连杆参与接触碰撞”需要分别取证。此处没有把该工程的默认策略推广为其他模型的建议。

## 引擎名称不代表相同控制语义

`engines.md` 区分三条路径：

| 原工程路径 | 原文描述的主要差别 |
|---|---|
| `isaac_physx` | 经 Isaac / PhysX 运行，作为参考路径。 |
| `isaac_newton` | 经 Isaac 的 Newton 包装层运行，输入与状态读回需要适配。 |
| `newton` | 直接构建 Newton 模型；求解器、可视化和资源注入职责与包装层不同。 |

原资料还分别讨论 mimic 约束、驱动存在性、运行时增益与状态读回来源。同名关节目标或同一组数值增益不自动证明语义等价。

**文档版本边界：** `engines.md` 的 newton-direct 控制描述与 `asset_consumption.md` / `param_injection_eval.md` 中的驱动参数讨论不完全处于同一抽象层次。本篇保留这项差异，不据此宣布当前实现统一采用某种控制律；复现时仍须回原工程核对指定版本的实际调用路径。

## 参数应落在能解释其生效时机的层

`param_injection_eval.md` 对比运行时 YAML、构建时 USD overlay 与适配器回退：

- 常规、需要反复调试的 PD 参数放在运行时配置，避免为每次调参重建模型。
- URDF 缺失的属性或模型特有的装配信息，需要明确其构建层来源。
- 适配器回退要说明何时触发，避免与已写入资产的参数重复覆盖。

这些是该版本文档的工程决策，未重新验证为当前上游最佳实践。原参数数值和参考模型文件没有随文导入。

## Newton 转换问题要绑定精确版本

`newton_quirks.md` 明确针对 `1.15.0.dev20260526`，记录了阻尼/刚度角度单位、关节与驱动限力、schema resolver、mimic equality 参数、关节范围和惯量主轴约定等转换风险。

其中包含“USD → 内部模型 → MJCF”的逐层观察，也保留了原文认为没有实际触发影响的条目，以及“吸附到相等惯量”“注入微小 rpy”等失败尝试。它们应作为该版本排查线索；本轮没有重新推导惯量变换或核验上游是否修复，不能把局部补偿写成跨版本规则。涉及数值调整的模型方案也不在本轮迁入时重新授予精度保证。

## 同步设计和验收结果必须分开

`ovrtx_sync.md` 开头注明 inline OVRtx 已实现，同时说明正文是原设计与实现考古笔记，草图签名并不代表实际 API。目标版本为 OVRtx 0.3.x，设计涉及 Newton 物理线程、渲染线程、GPU transform 数据与 CUDA stream 的握手。

该资料区分进程内可视化和现有跨进程渲染，讨论帧丢弃、背压、数据寿命、线程退出及物理/渲染负载相互影响。零拷贝的局部路径不能自动推出端到端零延迟或互不干扰。

原文列出的“物理吞吐差在 5% 内”“图像 SSIM > 0.99”“60 分钟稳定”等属于**验收方案或门槛**。本轮没有取得对应测试的完整结果，不能写成通过。G2 / UMI 文档使用的跨进程图像链路也不能直接继承 inline OVRtx 设计的性能预期。

## 性能复盘先统一统计对象

`perf.md` 区分 solver、完整 step、render、publish、tick interval、空闲预算和高分位长尾。可以保留的学习方法是：

1. 记录目标周期、是否包含渲染、是否含显式同步，以及测量的实际墙钟范围。
2. 区分渲染 tick 与非渲染 tick，检查均值之外的 P99、最大值和 deadline miss。
3. 用分段计时提出待核查的瓶颈，随后验证；一张均值表不足以定位调度、ROS、GPU 或碰撞服务。

原文的调优倍数、阈值和系统级命令具有环境前提，本篇没有将其迁入为本机操作清单。对应的最新实例可读 [回放卡顿与腰姿分析](umi-replay/PLAYBACK_ALIGNMENT_AND_WAIST_ZH.md)：原速、控制时限、HTTP 到达与浏览器呈现帧率须分别取证。
